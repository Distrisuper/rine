# Reglas de IA para el Proyecto RINE

## Estilo de Código
- Seguir PEP 8.
- Usar Type Hints en todas las funciones.
- Docstrings cortos en endpoints y servicios (1-2 líneas).
- Las entidades (modelos) que representen tablas y conceptos del negocio **deben tener comportamiento**. No son simples getters/setters. Aplicar **Tell, Don't Ask** (decir qué hacer, no preguntar estado).
- Evitar clases anémicas: toda entidad debe encapsular su lógica de negocio.

## Arquitectura - Principios SOLID
- **Responsabilidad Única (SRP):** Una clase debería tener solo una razón para cambiar.
- Interfacear siempre: no permitas dependencias directas en lógica de negocio.
- Inyección de dependencias para testabilidad.

## Testing & Capas
- Usa `unittest.mock` para simular servicios externos.
- Cada nueva funcionalidad **DEBE** incluir su archivo de test en `/tests`.
- Modelar respuestas externas con `TypedDict` o `BaseModel`.
- `HTTPException` solo en capa API, no en servicios.
- Convención de rutas: `/queue/...` y parámetros en `snake_case`.
- Documentar para Swagger siendo breve y consistente.

## Comunicación
- Sé conciso. Si el cambio es pequeño, no expliques toda la teoría.
- Si ves una violación de arquitectura, corrígela antes de implementar lo nuevo.
